Getting started

Install the release ZIP through WordPress Plugins, activate Gravity Forms, then open Forms → Settings → Gravity Presentation Profiles. GPP changes presentation; Gravity Forms still owns form data, validation, submission and permissions. Not every feature applies to every form.

Requirements and GTB coexistence

Gravity Forms and compatible host capabilities are required for form integration; operational views also require Gravity Flow and suitable real workflow data. For sites also using Gravity Theme Builder (GTB), choose one presentation owner per form. GPP does not install fonts, change Gravity Perks behavior or replace host controls.

Enable or disable presentation for one form

Open the chosen form → Settings → Gravity Presentation Profiles. Enable presentation, select one installed declarative profile or the legacy profile, then save. The declarative selection has priority when present. Turning GPP off preserves its selected profile but returns the form to the native appearance; it does not disable other forms or operational views.

Generic declarative profiles

A portable JSON package defines validated design tokens and supported presentation preferences; it does not contain executable custom CSS or workflow rules. Current generic no-code preference consumption is for gravity_forms.form. The shipped SRWF Inbox, Entry Detail and Print are distinct bounded operational implementations, not proof that they consume all generic form preferences.

Exact package vocabulary and limitations

The authoring contract uses schema 1.1.0 and requires artifact_type, schema_version, package_id, package_version, provenance, selected_surfaces, design_tokens, semantic_slots, surface_profiles, reserved_extension_seam. Supported form sections include composition, typography, controls, labels, descriptions, sections, primary_action and validation. Tokens include colors, spacing, radii, sizes, font sizes, weights and supported font families. Values and optional capabilities are constrained by the validator. Do not add arbitrary keys, host IDs, scripts or external URLs.

Offline LLM authoring prompt

In the General LLM Authoring Prompt section, expand or download the fixed prompt. Use it with an external LLM to produce package JSON only. You decide whether to share a screenshot; GPP sends no site or entry data and has no AI provider connection. This prompt is for creating packages; it is not the in-plugin user guide.

Import, validation and installed profiles

Paste one package JSON into Profile Package JSON and save. GPP validates its exact schema and lifecycle, then lists installed package/version/profile identities; the submitted JSON is not stored as a second settings copy. Invalid or unsupported JSON is rejected; correct it externally and retry. Selecting a profile does not invent missing data bindings.

Shared operational profiles and host ownership

Print, Inbox and Entry Detail can use one shared environment binding context for a selected real Gravity Forms form. Initialize operations only for that real form. GPP manages visual activation and explicit semantic binding; Gravity Flow remains the authority for workflow, assignments, Inbox queries, actions, pagination, navigation and authorization. Different active identities are reported instead of silently overwritten.

Initialize Print and use the native print utility

Under Operations Setup (Print), choose the actual form and save. This installs/adopts the shipped Print profile and starts with unmapped meanings; complete required field and raw-option mappings manually. Printing remains a native Gravity Flow entry utility and is allowed only when the host authorizes that user and request. The SRWF paper dossier has its own fixed Persian layout and is not a general report designer.

Initialize Inbox and work with native assignment

After preparing a compatible operations binding, select its form in Operations Setup (Inbox) and save. The SRWF presentation styles the native Gravity Flow Inbox; GPP does not create an assignment queue or change Search, pagination, Live Refresh or notification preferences. If readiness is not proven, inspect the setup result and mappings instead of forcing the presentation.

Entry Detail, review, correction and results

In Operations Setup (Entry Detail), adopt presentation for the same real form. The visual-variant selector changes appearance only; Current / Safe is the fallback design. The native Gravity Flow review, correction/User Input, approval, rejection and terminal result semantics still decide the available action. A visual message is not independent proof of a workflow transition.

Map meanings explicitly

Use Mapping & Binding Health to choose the exact Gravity Forms field or input for each admitted semantic meaning, then apply that row. For Print choice meanings, confirm the real raw stored option values rather than guessing from labels. Entry Detail batch mapping is an additional explicit path. A shared mapping can affect all consumers of that meaning, including Print, Inbox and Entry Detail.

Read binding and readiness states

Healthy means the source and evidence currently match. Unmapped means no source was chosen. Stale / source missing means a previously selected source is unavailable. Needs review or Evidence not proven means do not assume readiness; inspect source and host state. Not applicable is not a failure. Readiness facts never replace a real per-request Gravity Flow permission check.

Binding history and safe rollback

Each accepted mapping change creates and activates a new immutable binding version. In Binding history rollback, explicitly choose a previously authoritative version only if you intend to restore it; No rollback does nothing. This is separate from the Entry Detail visual Current / Safe selector. Re-check shared surfaces after a rollback.

Local diagnostics and support bundle

Diagnostics & Support lists recent presentation failures or fail-closed decisions. Use the sanitized JSON download only when you decide to share it; nothing is uploaded automatically. It excludes submitted values, uploads, passwords and request bodies. If diagnostics storage is unavailable, GPP attempts native host fallback rather than treating the missing log as success.

Permissions and practical troubleshooting

Use an account allowed to manage Gravity Forms settings for setup, mapping and diagnostic exports. A nonce protects the request but does not grant permission. If a profile is absent, check package import and exact version; if the UI is native, check the form enable switch and binding readiness; if an operation fails, read the explicit failure instead of retrying blindly. GPP does not override Gravity Flow access.

Updates, recovery and language

Back up WordPress and authoritative Gravity Forms/Flow data before replacing the plugin. Install a validated GPP release ZIP rather than a GitHub source archive. Preserve installed package identities and bindings; do not reset workflow data to repair appearance. This guide and GPP-owned admin text follow the WordPress administrator's locale (Persian or English), without a separate GPP language switch. Host-plugin text may use its own translations.
